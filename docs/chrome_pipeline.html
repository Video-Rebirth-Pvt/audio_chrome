01总览与阶段

Chrome-10B 是纯音频生成工程，前期只做文本生成音频（T2A）。 音频链路复刻 MiniMax-H3：同一套 Audio VAE、同一种单流 packed DiT、同一套 rectified flow。 视频放到 S5，但 AdaLN 三档和 MM-RoPE 的 h/w 轴现在就留着，后面加 VisualVAE 不改骨架。

MiniMax-H3、DiffSynth-Studio、VR-Foley-5.5B 只读。 本工程的代码、配置、脚本都在 Chrome-10B/。

02关键问题速答（先给结论，细节见后文）

每条先给一句判断，再给代码出处。“预留”指底层数据结构或接口已经有，但训练和推理链路没有用到； “估算”指按代码和 FLOP 推出来，没有在 GPU 上量过（8 张卡都在跑 10B 训练）。

Q1. 现在的链路能不能“给一段参考音频再生成”（同音色、续写、风格参考）？

不支持端到端只有 caption → 音频。数据、Task、推理 Pipeline 都没有“参考音频”这个输入； 当前 10B 权重也从没见过干净的音频条件行。底层按 H3 留了机制，但上面三层没接：

层位置现状
打包dit/packing.py · Segment(target, clean)预留clean=True 的行 AdaLN 的 t 钉成 1.0；target=False 的行不进 loss
DiT 前向dit/model.py · forward(t_rows [S])预留每行一个 t，AdaLN 按 unique t 查表
损失flow/objective.py · flow_loss(mask)预留只对 audio_target 行求 MSE
Layoutdit/layout.py · T2ALayout没有只产出 [text | 目标 L | 目标 R]，没有参考段
Tasktasks/t2a.py · t2a_flow_loss没有对 inputs.latents 全部加噪，没有“这段不加噪”的分支
推理pipeline/t2a.py · velocity()没有所有音频行都当目标去噪
权重outputs/train/t2a_10b没有没训过“目标行 attend 到干净音频行”，只改推理代码也不可靠

要支持需要五件事：新 layout、Task 只给目标段加噪、Pipeline 每步把参考行原样塞回、参考/目标配对数据、训练或微调。Euler 采样器本身不用改。改动清单见 §12。

Q2. 去噪能不能按条件选 token：部分行固定、部分行去噪，或者不同行用不同噪声水平？

模型能，链路没用DiT 的时间输入 t_rows 是逐行的 [S]，任意行都可以给不同的 t。 但现在的训练和采样都只用了最简单的形态：

  • 训练：一条样本一个 σ。左右耳、所有帧共用这个 σ（t2a_flow_loss）。
  • 文本行：不加噪，也不被采样器更新；但 AdaLN 用的是该样本音频的 t，不是 1.0（text_segment 的 clean=False）。
  • 采样：所有样本在同一步用同一个 σ，Euler 更新全部音频行，没有 mask。

所以 inpainting（固定前后补中间）、续写、diffusion forcing 那种逐帧不同 σ，都没有现成路径。机制上可行，但训练时要按同样方式构造样本。 还有一个代价：每行都给不同 t 的话，unique t 的个数 U 会涨到 S，每层 AdaLN 的输出 [U·3, 6·4096] 约 24.8k×3×24576×2 B ≈ 3.6 GB。所以 σ 要量化成少数几档。

Q3. “Qwen3-VL-32B / 前 50 层”到底取的是什么？是第 50 层，还是 50 层特征融合？

只取第 50 层的输出不融合，不拼接，不池化。

  • 只建语言模型的 embed_tokens + 第 1–50 个 decoder 层。第 51–64 层、最后的 norm、lm_head、视觉塔都不建，权重也不读（text/qwen.py · _wanted）。
  • model.norm 换成 Identity，所以 last_hidden_state 就是第 50 层输出的残差流，没有归一化。
  • 每个 token 一行，得到 [L, 5120]，L 是 caption 的 token 数（无 BOS/EOS，无 chat 模板）。
  • 进 DiT 前再经过可训练的 condition_proj（Linear 5120→4096，20.98M）和 2 层 token refiner（只在本条 caption 内做双向 attn + SwiGLU，无 RoPE、无 AdaLN，0.436B），最后 RMSNorm。两者都随 DiT 从头训练。图见 §09 图 4b。
Q4. 10.82B 参数主要在哪？

AdaLN 4.25B（39.2%） ≈ FFN 4.23B（39.1%） > Attention 1.88B（17.4%） > token refiner 0.44B（4.0%）> 其它 0.03B。

每个 token 实际走过的稠密参数只有主干的 6.1B。AdaLN 每步只对 unique t（约 32 个）计算，算力几乎为 0， 但占 39% 的优化器状态、checkpoint 体积和 FSDP 通信量。见 §14。

Q5. 训练时显存和耗时主要在哪？
  • 显存（每卡 allocated 92.8 GB）：Qwen 48.8 GB（约 53%）> FSDP 分片的权重/梯度/Adam/EMA 27.1 GB > 激活约 12 GB > VAE 等约 3 GB。
  • Qwen 为什么常驻：只要该 rank 有任意一条 caption 未命中磁盘缓存（outputs/text_cache），就会懒加载 Qwen3-VL-32B/50（48.8 GB）且常驻到进程退出。在第一轮（epoch 1）未命中率约 90%，text_s ≈ 0.56 s；到 100k 步末期磁盘命中率升至 >75%，text_s 降至 0.07 s；20s 扩窗续训时只对新出现的 15–20s 样本在线编码（约 15% miss），text_s ≈ 0.14 s。
  • 耗时（5.02–5.60 s/步）：DiT 前向+反传+优化 3.64 s（65–72%）> VAE 在线编码 1.35 s（24–27%）> Qwen 在线编码 0.07–0.56 s（1–10%）。见 §15 与 §16b。
Q6. 推理时显存和耗时主要在哪？（估算）
  • 显存：DiT 以 fp32 常驻 43.3 GB；autocast 在每次前向里还会缓存一份 bf16 权重，瞬时多出约 21.6 GB（机制已用小模型实测）； 有新 caption 时会加载 Qwen 48.8 GB，而且不释放；VAE 0.6 GB；激活 1–3 GB。峰值约 68 GB（caption 全在缓存里）或约 117 GB（有新 caption）。
  • 耗时：稳态下 95% 以上的计算是 DiT 50 步 × CFG 双份序列。Qwen 每条 caption 只算一次（约 3 TFLOP）；VAE 解码 10 s 立体声约 1 TFLOP。 冷启动要读约 92 GB 权重，第一次调用往往比生成本身还慢。见 §15。
Q7. 文本行在 DiT 里做什么？推理时每步都重算吗？

文本行和音频行在同一条序列里做双向 self-attn：同一样本内全可见，样本之间隔离。28 层都会更新文本行，只是最终层只取音频行输出。 推理时文本行每步都重算，因为 AdaLN 用当前 t 调制文本行，不能像 cross-attn 那样缓存 K/V。 refiner 的输出与 t 无关，理论上可以缓存，代码目前每步重算（计算量很小）。

Q8. 能生成多长？能出单声道吗？

第一阶段 t2a_10b 训 4–15 s 整秒（已完成 100k 步）；第二阶段 t2a_10b_s20 将 audio.max_seconds 扩到 20 s（4–20 s 整秒，正在训练）。推理 CLI 按所加载 run 的 config.yaml 把秒数夹到 [min_seconds, max_seconds]（train/cli.py · _prompts）。 输出固定 2 声道（audio.channels=2）；需要单声道就取 L 或 (L+R)/2 做后处理。

Q9. TensorBoard 训练面板里的 train/cond_s、train/data_s、train/gn/adaln、train/gn/condition_proj 分别代表什么？
  • train/data_s（稳态 ~0.0009 s）：主进程从 12 个后台 CPU DataLoader worker 的预取队列取走一个已组装好 batch 的等待时间。<1 ms 代表 CPU 读盘、重采样、分词 100% 被 GPU 计算掩盖。
  • train/cond_s（稳态 1.41–1.91 s）：GPU 在 no_grad 下完成条件准备的总耗时，严格等于 vae_s（冻结 AudioVAE 按整秒分桶编码，~1.35 s）+ text_s（查缓存 + 未命中时跑 Qwen3-VL-32B/50，0.07–0.56 s）+ pack_s（~0.005 s）。
  • train/gn/adaln（稳态 ~0.005–0.006）：占全模型 39.2% 参数（4.25B）的所有 AdaLN 层在梯度裁剪前的 L2 梯度范数。从零训初期在 step 200 冲到 0.81（破除零初始化打开 gate），收敛后仅占总梯度范数（~0.05）的约 1/8；热启动扩窗（s20）时随 1000 步 LR warmup 从 0.0038 爬升至 0.0061。
  • train/gn/condition_proj（稳态 ~0.0018）：仅占 0.19% 参数（20.98M）的文本入口投影层 Linear(5120→4096) 的梯度范数。用于监控 ① 音频行对文本行的跨模态注意力梯度是否畅通（不为 0）；② Qwen 第 50 层第 0 个 token 的 15872 巨型激活（Massive Activation）是否引发梯度爆炸。完整图文拆解见 §16b 训练监控曲线深度解读。

Euler 50 · CFG 4 是什么（训练里的 3 不是 CFG）

配置里同时有三个「3 / 4 / 50」，不要混

训练日志或 yaml 里看到的 3 是 flow.shift=3.0（噪声日程）， 不是 classifier-free guidance。 训练阶段没有 cfg_scale，只做 10% 空 caption； cfg_scale=4 和 steps=50 只在 preview / infer 生效。

你看到的数配置键训练推理 / 听评实际在干什么
shift = 3 flow.shift 3 3（必须相同） 把均匀时间 u 拧成 σ：σ = 3u / (1+2u)。质量偏向中高噪声。H3 音频就是 3，视频才是 12；上一版 VR-Foley 是 5，不要混用
cfg_drop = 0.1 data.loader.cfg_drop 10% 换成 " " 不用 让 DiT 见过无条件速度 v(x, ∅)。空条件是单个空格（token 220），和 H3 negative_prompt 一致，不是把 embedding 置零
CFG = 4 preview.cfg_scale / infer.cfg_scale 无（没有 guidance 缩放） 4.0 每步双前向：v = vu + 4·(vc − vu)。从零训必须在推理开 CFG；H3 发布权已经蒸馏过，官方推理才是 1.0
Euler 50 preview.steps / infer.steps 每步只抽 一个 σ，做一次速度回归 50 步从 σ=1 走到 0 确定 ODE（η=0），日程仍用 shift=3。H3 默认 50 步；rectified flow 轨迹接近直线，50 已经够听。S4 再蒸少步

训练一步在算什么

u ~ Uniform(0,1)
σ = 3u / (1+2u)          # shift，不是 CFG
xσ = (1-σ)·x0 + σ·ε
v* = ε - x0
pred = DiT(xσ, caption 或 " ")
loss = MSE(pred, v*)     # 一次前向，没有 50 步

听评 / 推理 50 步在算什么

x ← ε ~ N(0,I)
for k in 0..49:          # Euler η=0
    vc = DiT(x, caption)
    vu = DiT(x, " ")     # 同一 packed 序列里一起算
    v  = vu + 4*(vc-vu)  # cfg_scale
    x  ← x + (σ_{k+1}-σ_k)·v
decode(unwhiten(x)) → wav

为什么定成这些值： shift=3 和 50 步是跟 H3 音频日程对齐，AdaLN 训练和推理看到的 σ 表一致。 CFG=4 是从零训 T2A 的听评默认（上一版模型用 guidance 4.5 / 30 步；音频 flow 常见 3–5）。 偏小更稳、更糊，偏大更跟 prompt、更容易金属声和过饱和。这不是训出来的超参，是听评起点；S2 消融可以扫 2/3/4/5，S4 蒸馏后推理应回到 CFG=1。

这次 10B 和旧文档 16k 口径的差别

开训前段用过 max_tokens=16384（约 21 条/卡、3.8 s/步、82 GB）。 当前配置和稳态日志都是 24840（约 32 条/卡、5.6 s/步、92.8 GB allocated）。 token/秒几乎不变，变的是一步的全局 batch（165 → 253 条）。详见 §16。

06数据处理

清单 → 每个数据源一份 Arrow 索引 → 按权重混合、按 token 预算打包的 batch → 在线读波形 → 冻结 VAE 在线编码（不存 latent）。 参数全在 configs/data/t2a_base.yaml，数据源列表在 configs/data/sources_vrfoley.yaml。 比 VR-Foley 的 audio_pretrain 多做的：索引一次建好、内存映射共享，不在每个进程里装整份清单； 所有行都能被抽到，不再先随机截 max_records 子集；一个包里混合时长，按 token 预算装满；续训能接上下一个 batch。

1. 索引与多格式清单（一次性，scripts/data/build_index.sh / repack_audio.sh）

  • 多源清单组合（data.include）：configs/data/t2a_base.yaml 通过 data.include: [sources_vrfoley.yaml] 引入源列表；叠加新语料只需像 configs/data/t2a_worldspeech.yaml 那样追加 sources_worldspeech.yaml，自动按顺序合并 sources。
  • 列名自适应与分块并发：清单支持 JSONL 或 Parquet，文件或目录都行。列名先用 columns 里配的，再退回候选：音频 path / audio / audio_filepath / wav，caption resp / caption / normalized_text / text，时长 duration / audio_duration。JSONL 按 64 MB 字节块、Parquet 按 row group 多进程扫描。每行依次检查 keep 条件、音频路径、caption、preview 排除列表、坏文件列表、时长（缺了读文件头）、长度策略、caption ≤ 512 token；每种丢弃原因都计数写进 meta.json。
  • 伴生 QA 表按行校验连接（sidecar）：针对 WorldSpeech 等将质检指标分拆在同名 *_qa.parquet 的数据集，源配置支持 sidecar: {suffix: _qa.parquet, key: id, columns: [duration, dnsmos_ovrl, ...]}（chrome/data/manifest.py · _join_sidecar）。按 row group 读入伴生列，并逐行校验主键 id 完全一致后拼回主表，再统一走 keep 过滤。
  • Parquet 内嵌音频零拷贝转存（chrome/data/blobs.py + scripts/data/repack_audio.sh）：HuggingFace 风格 Parquet 把音频字节嵌在 audio.bytes 里，训练时若直接随机读 Parquet 必须解压整个 row group，会导致 data_s 飙升。repack_audio.sh 一次性把音频字节流式转存到未压缩的 *.arrow（单列二进制 blob），并写出轻量 manifest.parquet（将音频列改写为虚拟 URI arrow:///abs/path/part.arrow#row，同时把伴生 QA 列并入）。建索引与训练时，audio_io.py · _arrow_bytes 通过进程级缓存的 pyarrow.memory_map 零拷贝切片出对应字节，再交由 soundfile 解码。
  • 指纹校验与确定性划分：产物存放在 outputs/data/index/<source>/{index.arrow, meta.json}（20s 扩窗使用独立目录 outputs/data/index_s20）。配置指纹（含 min/max_seconds、keep、max_records）和清单 mtime/size 都没变就跳过；改 weight 不用重建，改了影响行内容的字段，loader 启动会报错提示重建。去重和验证集划分都看音频路径的 blake2b 哈希：同一路径只留一条；哈希落在每百万 holdout_ppm（500）以内的行留作验证，加数据不改变已有行的归属。

3. 采样与打包（MixtureBatchSampler）

max_tokens 是单卡预算，不是全局 batch

每个 rank 各自打一个包，上限 data.loader.max_tokens（这次 10B 是 24840）。 8 卡一步的全局规模是 8 个独立的包：大约 8 × 24840 行、253 条音频，不是「8 卡共享一个预算」。 日志里的 clips/rank 是每卡条数，fill 是本卡 24840 里有效行的占比。

  • 每抽一条，先按 weight 选源，再取该源 shard 的下一行。shard = 本 rank 在按 (seed, 源名, 源 epoch) 打乱的排列上取 [rank::world]，同一 epoch 内各 rank 不重叠，小源只是更快进入下一个 epoch。
  • 每条代价 = 80 × 秒 + caption token 数（80 = 每秒 40 帧 × 左右耳）。贪心往当前包里塞，累加到 max_tokens 就封包。
  • 临界超限不截断。 再塞下一条会超过 max_tokens（这次 24840；或条数到 max_samples=64），这条完整放进 _carry，下一包原样接着用。当前包带着不满的 token 去训。日志 fill≈0.976 就是经常差最后一条装不满；差的那截只是整包再补到 64 的倍数，不是把某条音频砍短。
  • 单条自己的代价已经大于 max_tokens 时，sampler 启动直接报错，不会默默截断。当前上限 caption 512、最长 15 s，代价最多约 80×15+512=1712，远小于 16k。
  • 一个包里时长混合（4–15 s）。波形保持各自长度；DiT 按样本切 cu_seqlens，样本之间互不看见。VAE 只拼等长片段再编码，见下方警告框。
  • 续训：训练器存 sampler.state_dict(batch["batch_id"])，恢复后从下一个 batch 接着出；取窗位置和 caption dropout 由每条样本的种子决定，也一样。某个源重建过索引，只有它从下一个 epoch 重来。中途改 max_tokens 会改变封包切分，续训对不齐当前 sampler，应另开 run。

按 token 预算而不是固定条数，是为了把每步的算力和显存钉在序列长度上。 4 s 和 15 s 对 DiT 的代价差约 4 倍；固定 bs=N 要么按最长 pad 空算，要么只能抽同长度。 这次 10B 用 24.8k 打包：每卡大约 32 条、填充率 0.976，步时和显存都稳。16k 干跑时是 21 条 / 0.97。

4. 读取（DataLoader worker）

  1. 读文件：要裁的只解码需要的窗口（soundfile seek，不行再用 torchaudio.load(frame_offset=…)）； 其余整段读，soundfile 失败再 torchaudio。解码失败的路径追加进 outputs/data/bad_audio.txt（加文件锁），换同源随机一条。
  2. 折成立体声：to_stereo，见 §08。
  3. 重采样：到 32000，sinc 核按采样率对缓存（和 torchaudio.functional.resample 差 < 1e-4）。 16 kHz 语音库升到 32 kHz 后 8 kHz 以上没有能量，配比过大会拉低高频。
  4. 长度与峰值：裁或补到整秒；峰值超过 0.95 才整体缩小，更小的不放大（同 VR-Foley，data.peak）。
  5. caption：H3 tokenizer 编码；10% 换成 " "（token 220）做 CFG。

07VAE：输入、输出、结构、Decoder

chrome/codec/ChromeAudioVAE 复刻 H3 Audio VAE。 state dict 键名一致，原始权重 strict=True 直接加载，没有改名钩子。 结构：DAC 编码器 → 因果注意力瓶颈 → 对角高斯 → BigVGAN 解码器。

网络本身是单声道

in_channels=1。立体声折进 batch 维：[..., C, N] → [-1, 1, N]。 左右共享全部权重，codec 内部不混合左右。 入口 encode_audio / decode_audio 负责折、拆、白化。

接口（已实现）

vae = load_h3_audio_vae(paths.h3_audio_vae, device="cuda")

# 推理 / DiT 用：只要白化后的后验均值，不采样、不带梯度
latent = vae.encode_audio(wave)      # [..., C, N] → [..., C, 32, ceil(N/800)] float32
wave   = vae.decode_audio(latent)    # [..., C, 32, T] → [..., C, T·800]

# 训练 VAE 用
recon, posterior = vae.forward(audio, sample=True)   # posterior.logs 是 log σ
# encode_posterior → DiagonalGaussian(mean, logs)

2. VAE：L/R 完全不混合

  • 输入 L≡R ⇒ μ_L ≡ μ_R（确定性 encode，误差为 0，对齐检查已过）。

  • 白化统计是「编码器输出空间」的 32 对，不是左右各一套。
  • 批量 [B, 2, N] 与逐条编码逐位相等。

S5 前要在三条里选一条： 保持 H3 原样，T2A 固定 16:9； 保持绑定，但 T2A 按 S5 计划的画幅集合随机抽 w； 或者解绑，音频 w 固定成一组与画幅无关的值。 RoPE 的 w 只是软偏置，不是 mask（见 §11），所以绑定的收益要等有视频数据时才能验证。

为什么要有它

  • Qwen 是冻结的：只靠一层线性映射，DiT 只能对 Qwen 特征做旋转和缩放。refiner 提供 0.44B 参数，专门把文本特征改写成音频生成好用的形式，而不用去动 32B 的编码器。
  • Qwen 是因果的：第 i 个 token 的特征只看过前 i 个词。refiner 的双向注意力让每个 token 看到整句。主干里文本行之间也是双向的，但那里的文本行同时受 t 调制、和音频混在一起。
  • 先把文本处理好，再和噪声混：refiner 不接收 t，文本表示在所有噪声强度下是同一份；进了主干之后才按 t 调制。
  • 以上是设计上的解释。结构和参数名照搬 H3（DiffSynth MiniMaxH3DiT 的 condition_proj / token_refiner，同样 2 层），H3 没公开去掉 refiner 的消融。

训练与梯度

  • 都训练，从头训：它们是 ChromeDiT 的子模块，requires_grad=True。初始化是 Xavier 权重、零 bias（init_weights），train.init_from: null，不加载 H3 权重。
  • 和主干同一套设置：AdamW lr 1e-4，矩阵权重 weight decay 0.01，bias 和 RMSNorm 的 γ 不加；梯度裁剪 1.0；EMA 0.9999；fp32 主权重、bf16 计算；一起存进 checkpoint 和导出的 ema.safetensors。
  • 梯度只到这里：Qwen 的输出要么从缓存读，要么在 no_grad 下算，是常量，所以反传停在 condition_proj 的输入。
  • 训练日志：gn/condition_proj 在第 20 步是 0.0000，第 40 步 0.0001，第 11.6k 步 0.0037，第 24.3k 步 0.0026（同期总梯度范数约 0.088）。 一开始是 0，是因为 AdaLN 的门和 audio_out 都零初始化：文本只能通过主干的注意力影响音频，门关着时梯度传不回来。门打开后它才开始学。
  • 代价：参数占 4.2%；每个文本行前向约 0.91 GFLOP，按每卡每步约 1.8k 文本行算约 1.7 TFLOP，约为主干的 0.5%；按 20 B/参数算训练状态约 9 GB，8 卡分片后每卡约 1.1 GB。
S2 要消融：Qwen 规模主要是算力问题

截断 32B 编码一条约 200 token 的 caption 约 10 TFLOP；1B DiT 训一个 15 s 样本约 7 TFLOP，10B 约 55 TFLOP。 在线编码时，1B 消融里 Qwen 比 DiT 本身还贵，10B 也要多出约 18%。 离线缓存每条 = L × 5120 × 2 B。这次数据均值约 56 token，每条约 0.58 MB，1010 万条约 5.9 TB（200 token 的长 caption 每条约 2 MB）。 1B 消融比较更小的 Qwen3-VL 和截断 32B；保持 VL 系列，S5 才有现成的视觉语义通路。

13Flow matching 与采样（已实现，chrome/flow/）

项约定
形式Rectified flow：x_t = (1−σ)·x0 + σ·ε，目标 v = ε − x0
σσ = s·u / (1 + (s−1)·u)，u ~ Uniform。训练和推理用同一个 shift
音频 shifts = 3（H3 视频是 12）。这不是 CFG，见 §03
AdaLN 时间t = 1 − σ
σ 的粒度训练：每条样本一个 σ，左右耳、所有帧共用，文本行的 AdaLN 也用这个 t；同一包里不同样本各抽各的。推理：一步里所有样本同一个 σ
干净 / 参考行机制预留：clean=True 的行 t 钉 1.0，target=False 的行不进损失。T2A 不产生这种行（§12）
时间嵌入t ∈ [0,1] 直接乘频率进 sin/cos（256 维，最长周期 10⁴），不先乘 1000。与 H3 一致：DiffSynth 的 H3 pipeline 里是 t = 1 − timestep/1000
损失音频行上的速度 MSE：(pred − (ε − x0))²，文本行和 pad 行不算。默认 flow.loss_reduction: token
采样器Euler，η = 0，推理 50 步。训练每步只抽一个 σ，不跑这 50 步。preview.sampler / infer.sampler 切换，S4 的少步采样器加在旁边

一个包里时长混合时，默认按音频行平均，不是按条平均。 每行（一帧、一个声道、32 维）先算 MSE，再 loss = Σ(行 MSE) / 音频行数。 15 s 立体声是 15 × 40 × 2 = 1200 行，4 s 是 320 行，所以 15 s 对总 loss 的贡献约是 4 s 的 3.75 倍。 算力花在更长的音频上，梯度也按行数给。随机初始化时 loss 大约 1.2–1.3，没有「正确率」含义。

红框 1 · train/cond_s（截图值：1.5149 s，波动区间 1.48 ~ 1.515 s）

1. 代码定义与精确构成

在 chrome/train/trainer.py 第 250–262 行中，cond_s 测量的是 prepared = self.task.prepare(batch) 的端到端墙钟时间。 进入 chrome/tasks/t2a.py · encode_t2a（第 44–53 行）后，它在 @torch.no_grad() 下串行执行三件事，满足恒等式： 

cond_s  =  vae_s (1.3675 s, 90.3%)  +  text_s (0.1423 s, 9.4%)  +  pack_s (0.0049 s, 0.3%)  =  1.5149 s
  • vae_s ≈ 1.35–1.37 s（占 cond_s 的 90%）：冻结的 H3 Audio VAE 编码器在 GPU 上以 fp32（禁 TF32）在线编码本卡约 29 条立体声波形（合计约 280 秒音频）。由于不同秒数的波形补零混编会污染末尾 ~10 帧 latent（见 §06），encode_waves 按整秒长度（4..20 s）分桶依次跑编码器前向。
  • text_s ≈ 0.14 s（占 cond_s 的 9.4%）：CachedTextEncoder 依次查本进程内存 LRU（4096 条）→ 磁盘 outputs/text_cache/*.safetensors → 未命中时跑冻结的 Qwen3-VL-32B（前 50 层）并原子写盘。
  • pack_s ≈ 0.005 s（0.3%）：T2ALayout.pack 在 CPU 上生成 token_tags、fp64 3D RoPE 坐标 positions、cu_seqlens 并搬上 GPU。

2. 为什么曲线形态是「step 20 尖峰 → 稳态在 1.48~1.51 s 窄幅锯齿震荡」？

  • 左侧起点冲顶尖峰（step 20 达 2.93 s）：训练刚启动时，各 rank 首次遇到未缓存的 caption，触发 Qwen3VLTextEncoder._load() 从磁盘读取 48.8 GB 的前 50 层权重，这笔一次性懒加载耗时被平摊进了首个 20 步窗口的 text_s 和 cond_s。
  • 为什么在 t2a_10b_s20 中是 1.50 s（对比 15s 开训时的 1.91 s 和 15s 100k 步末期的 1.41 s）：完全由新增 15–20 s 样本的文本缓存未命中率决定！在 s20 的 step 1280 处，单卡累计 disk=28,167（4–15 s 老样本直接命中 100k 步留下的磁盘缓存）、memory=3,732、encoded=5,385（新纳入的 15–20 s 语音样本从未见过，约占 14.4%）。每步每卡约有 4 条新 caption 需要现场跑 Qwen，耗时约 0.14 s；加上恒定的 vae_s ≈ 1.36 s，正好落在 1.50 s。
  • ~30 ms 的上下锯齿：① 每包内抽到的 15–20 s 未缓存新样本条数随机波动；② 每包内 4–20 s 出现的不同整秒桶数不同（桶越多，VAE 小 batch kernel 启动次数越多）。

3. 算法开发怎么看这条线

cond_s 占了总步时的 29%，且其中 90% 是 vae_s。若做小模型（如 1B）架构消融，cond_s 甚至会超过 model_s 成为第一瓶颈。改进方向：在 T2ATask.prepare 中支持离线 latent 缓存或用独立 CUDA stream 将下一步的 encode_waves 与当前步的 model_s 异步重叠，可直接削去 ~1.35 s/步。

红框 2 · train/data_s（截图值：0.0009 s，纵轴范围 8e-4 ~ 9e-4 s）

1. 代码定义：为什么读 29 条音频只花 0.9 毫秒？

在 chrome/train/trainer.py 第 248–258 行中，data_s 测量的是主进程执行 batch = next(data_iter) 的阻塞等待时间。 它测的不是 CPU 从硬盘读音频的实际耗时，而是「GPU 消费速度 vs CPU 预取生产速度」的差值！

  • 每个 GPU rank 背后有 num_workers=12 个常驻 CPU 进程（prefetch_factor=4, persistent_workers=True, pin_memory=True）。
  • 当 GPU 在跑前一步的 cond_s + model_s（共 5.2 秒）时，12 个 CPU worker 早已在后台并发完成了：Arrow mmap 寻址 → soundfile 窗口 seek（或 arrow:// 零拷贝切片）→ to_stereo → 32kHz sinc 重采样（核缓存）→ 0.95 峰值限制 → H3 tokenizer 分词，并把组装好的 collate_t2a 字典放进了共享内存的预取队列。
  • 因此主进程调用 next(data_iter) 时直接从队首拿走现成引用，只花 0.8 ~ 0.9 ms（占单步时间的 0.017%）。

2. 曲线形态与工程故障诊断

  • 正常形态（如图）：仅在 step 20 有一根冲出画面的竖线（0.315 s，worker 进程首次 fork 与初始化重采样核的冷启动），此后全程贴在 8e-4 ~ 9e-4 s（亚毫秒级），证明 IO 与 CPU 预处理被 100% 掩盖，GPU 零饥饿。
  • 异常报警（开发新数据管线必看）：如果加入新数据源或在线数据增强后，看到 train/data_s 从 1e-3 抬升到 > 0.05 s 甚至出现周期性大尖峰，说明后台 12 个 worker 产速跟不上 GPU。常见原因：① 直接读取了未用 repack_audio.sh 转存的 HuggingFace 内嵌音频 Parquet（每次随机读被迫解压整个 row group）；② MP4/压缩音频未走窗口 seek 而触发了全文件 ffmpeg 软解；③ 在 T2ADataset.__getitem__ 里写了未缓存的慢速算子。

1. 代码定义与精确计算时机

在 chrome/tasks/t2a.py 第 117–123 行中，T2ATask.grad_groups 将所有参数名包含 "adaln" 的可训练参数归入该组（包括 28 个主干块的 blocks.*.adaln_proj.linear 和最终层的 final_layer.adaln_proj.linear，合计 4.247B 参数，占全模型 10.822B 的 39.24%）。 每 log_every=20 步，在反传结束、全局梯度裁剪 clip_grad_norm(1.0) 之前，trainer.py 第 270–273 行调用 parallel.grad_sq_norm(params).sqrt()，在 fp32 下跨 8 卡 FSDP 分片做 all-reduce 求精确的未裁剪 L2 范数： gn/adaln = sqrt( Σ_{p ∈ AdaLN} ||∇_p L||_2^2 )。

3. 对算法开发的启示：为什么 39.2% 的参数只产生 ~1.5% 的梯度能量？

在稳态下，全模型总梯度范数 grad_norm ≈ 0.049（平方和 ≈ 2.4e-3），而占了 39.24% 参数量（4.25B）的 AdaLN 梯度范数只有 0.0061（平方和 ≈ 3.7e-5，仅占全模型梯度平方能量的 1.5%）！ 原因在于：AdaLN 的输入只是标量时间步 t ∈ [0,1] 的正弦嵌入（自由度极低），一旦学好随噪声水平 σ 平滑缩放的曲线，它的梯度就会大幅收敛；中后期 98% 以上的梯度都在更新主干 Attention 与 SwiGLU FFN。 这从梯度实测上证明了每层独立放一个 151M 的 AdaLN 存在严重参数过剩，直接支撑了 S2 将 dit.adaln=shared（AdaLN-Single：全局共享大投影 + 每层轻量偏置，省下 ~4B 参数）作为核心结构改进方向。

红框 4 · train/gn/condition_proj（截图值：0.0018，波动区间 0.0014 ~ 0.0034）

1. 代码定义：为什么专门监控这一个仅占 0.19% 参数的小线性层？

在 chrome/tasks/t2a.py 第 120 行中，gn/condition_proj 单独提取了 ChromeDiT.condition_proj（nn.Linear(5120, 4096, bias=True)，仅 20.98M 参数，占全模型 0.19%）在裁剪前的 L2 梯度范数。 它是冻结的 Qwen3-VL-32B 第 50 层输出（[ΣL, 5120]）进入可训练 DiT 的第一道咽喉门户（见 §09 图 4b）。专门把它拎出来画一条曲线，有两个不可替代的算法诊断目的：

  • 目的 ①：监测「跨模态注意力通路」是否畅通（防止条件坍缩）
    在单流 ChromeDiT 中，文本行在最后一层 FinalLayer 被直接丢弃，不直接参与 MSE loss。 condition_proj 要拿到梯度，唯一的路径是：音频行的 MSE 梯度 → 在 28 层 DiTBlock 的双向 Self-Attention 中通过音频行对文本行的注意力权重反传到文本行的 K/V → 穿过 2 层 TokenRefiner → 反传到 condition_proj。 在从零训练（t2a_10b）的第 20 步，因为主干 AdaLN 的 gate 还是 0，音频行看不见文本行，gn/condition_proj 只有 3e-6（几乎为 0）；随着 step 200 门打开，它跃升至 0.094，并在稳态保持在 0.0015 ~ 0.0030。 如果在算法实验中发现 gn/condition_proj 跌向 0，说明模型发生了“条件坍缩”（忽略文本 prompt、退化为无条件音频先验）。
  • 目的 ②：盯防 Qwen 第 50 层「Massive Activation（巨型激活值）」引发梯度爆炸
    如 §09 实测，Qwen 第 50 层没有经过 RMSNorm，每条 caption 的第 0 个 token 在第 731 维恒定有一个约 15872 的巨型激活值（整行 RMS 约 224，是普通 token 的 50 倍）。 对于线性层 y = x W^T + b，权重的梯度为 ∇_W L = (∇_y L)^T x——输入 x 的第 731 维放大了 3000 倍，导致 condition_proj.weight[:, 731] 这一列的梯度占了整个 condition_proj 梯度平方和的 ~75%（直到 2 层 TokenRefiner 末尾的 final_norm 才把每行尺度拉平）。 在 10B 默认配置 dit.text_norm: none 下，gn/condition_proj 稳定在 0.0014 ~ 0.0034 无尖峰，证明 bf16 + final_norm 完全能稳住这颗巨型激活。

2. 单位参数梯度密度对比（为什么 0.19% 的参数有这么可观的梯度？）

对比红框 3 和红框 4：condition_proj 的参数量（20.98M）只有 AdaLN（4247M）的 1/202，但它的梯度范数（0.0018）却达到了 gn/adaln（0.0061）的 30%！ 如果计算每个参数的平均梯度均方根（||g||_2 / sqrt(N_params)），condition_proj 的单位参数梯度强度是 AdaLN 的约 60 倍。 原因正在于它直接承受了 Qwen 未归一化残差流的大幅值输入，且承担着把因果 LM 表示对齐到声学空间的繁重任务。

模型构建与 FSDP2

  • 在 meta device 上建模型（10B 约 1 s，不占内存）→ parallel.setup 先分片，再 to_empty 物化，再用同一种子调用 init_weights。init_weights 覆盖所有参数和 buffer，能处理 DTensor；meta 上初始化和直接在设备上初始化结果相同（有单测）。
  • fully_shard：每个 refiner block 和主干 block 各是一个分片单元，root 最后分片。fp32 主权重 / 梯度 / Adam 状态按分片存，bf16 计算，fp32 reduce。
  • cast_forward_inputs=False：RoPE 位置是 fp64、时间步要全精度。
  • root 也设 reshard_after_forward=True；验证、preview、EMA 换权重前后显式 parallel.reshard()。
  • 所有 rank 前向次数必须一样：验证 batch 少的 rank 补跑重复前向；preview 平均分到各 rank，不够的用最后一条补齐。
  • EMA 只存本 rank 的分片（fp32），存盘时包成 DTensor；preview 用 ema.swapped()。
  • HSDP：shard_size=S 时建 ("replicate","shard") 二维 mesh。多机设成 8：机内分片、机间复制。
  • DDP 设 broadcast_buffers=False，验证和 preview 走未包装的模型。

19b · Preview 语音可懂度：ASR 错误率（chrome/eval/asr_preview.py）

preview 里有十几种语言和方言，靠耳朵听判断不了"说的是不是 caption 里那句话"。这一步用 Qwen3-ASR-1.7B 把每条 [SPEECH] preview 转成文字，再和 caption 里的对白比对，得到一个可以跨 step 画曲线的数值。 评测在 qwen3-asr 环境里离线运行，不进训练进程：训练卡显存已占 100–140 GB，而且两个环境的 torch / transformers 版本不同。

链路

samples/step_X/*.txt 里的 caption，只取 [SPEECH]: <d>[Lang][方言][性别]… 正文</d> 这一类， 正文作为参考文本，第一个标签作为预期语言 → 同名 wav 送 Qwen3-ASR，不指定语言，得到识别出的语言和识别文本 → 两边做同一套归一化 → 按语言选字或词做 Levenshtein 对齐，数出替换 S、删除 D、插入 I。 纯音效、纯音乐和 [MUSIC] 歌词条目不参与打分。

错误率怎么算

单条错误率 err = (S + D + I) / N，N 是参考文本的长度（字数或词数）。0 表示完全一致。 插入多的时候（比如 ASR 输出了一大段重复）单条可以超过 1。

语言单位原因
Chinese、Cantonese、Japanese、Korean、Thai字（CER）没有可靠的词边界；韩语参考文本本身就不带空格
English、German、French、Spanish、Russian、Arabic 等词（WER）空格分词，跟业界 TTS 评测口径一致。每条另外也算一份 CER

归一化对参考文本和识别文本完全对称，只消除"写法不同、读音相同"的差异：

  • NFKC（全角转半角）+ 统一小写，去掉标点和撇号，空白合并。
  • 繁体转简体（zhconv）：台湾、粤语的参考文本是繁体，ASR 可能输出简体。
  • 阿拉伯语：去掉元音符号，统一 أ/إ/آ→ا、ة→ه、ى→ي、ؤ→و、ئ→ي。参考文本本身就是这种折叠写法。
  • 粤语折叠（只对标签为 [Cantonese] 的条目）：caption 是书面语，Qwen3-ASR 写的是粤语口语字。 两边都把约 40 个口语字词转成书面字（喺→在、嘅→的、系→是、佢哋→他们、啲→些、冇→没有、唔→不、嗰个→那个、点解→为什么、而家→现在…）， 再去掉句末语气词（啊、呀、啦、喇、啰、咯、喎、㗎、啩、嘛、哦…）。不做折叠的分数另存为 err_strict。

配置约定

  • OmegaConf。_base_ 可以是路径或列表，按顺序合并，自身最后合并；再套命令行 key=value，再解析 ${...}。
  • 相对路径从 Chrome-10B/ 根算。脚本先 cd 再 source scripts/env.sh。
  • 外部路径只写在 configs/_base_/paths.yaml：H3 根、两种 VAE、文本编码器、tokenizer、DiffSynth、VR-Foley、音频数据根、preview、输出目录、数据索引目录。
  • 列表里有 ${...} 插值时写块列表（- ${paths.x}）；写成 [${paths.x}] YAML 会解析失败。

已知坑

  • 系统 python3 没有 safetensors，要用 ovi（scripts/env.sh 里的 PYTHON）。
  • 直接 import diffsynth 会去拉 modelscope。对齐检查在 sys.modules 里塞空包，只加载 minimax_h3_audio_vae.py。DiffSynth 加载前，pre_block.attn.{q_bias,v_bias,zero_k_bias} 要加 .weight 后缀。
  • 官方 bundle 的 MiniMaxH3AudioVAE 只暴露 decode；编码得手动走 .model 的 encoder → pre_block → mean_proj。
  • 对齐必须关 TF32。打开时 decode 对官方 1.1e-3，encode 对 DiffSynth 4.9e-2；关掉才进 1e-4。
  • GAN 重建看频谱（mel_l1），不要看 SI-SDR。
  • VAE 批量编码只拼等长片段；补零后一起编码，被补片段最后约 10 帧 latent 会变。
  • H3 tokenizer 要经 AutoTokenizer.from_pretrained(目录) 加载，直接读 tokenizer.json 会把 <d> 拆开。
  • 建索引主要花在 caption 分词；encode_batch_fast（不算 offset）快约 2.7 倍，id 相同。
  • 内嵌音频字节的 Parquet（如 WorldSpeech）不要直接在训练时随机读，必须先用 repack_audio.sh 转成未压缩 Arrow Blob，否则每次随机读解压整块 row group 会拖垮 DataLoader。
  • FSDP 下所有 rank 的前向次数必须相同，否则卡在 all-gather 直到超时；新加的验证 / preview 逻辑都要补齐。
  • FSDP 的 MixedPrecisionPolicy 默认把前向输入转成 bf16，会损失 RoPE 位置和时间步的精度；要设 cast_forward_inputs=False。
  • root 不 reshard 的话，no-grad 前向后会留着已经 gather 的旧权重，EMA 换权重会失效。
  • 10B 关掉激活重算会 OOM（16k token/卡）。
  • run 目录已有 checkpoint 时，重跑同一命令会续训；要从头开始，加 train.resume=null 或换 train.run_name。
